# Карточка П1 — опись muse для личного агента

**Кто читает:** ревизор и инженер — по описи строится весь план (П2–П5).
**Решение:** что берём у muse как есть, что идёт через прослойку модели, чего у агента нет.
**Нормально:** каждая вещь muse названа с файлом и строкой; привязки к Claude перечислены все, а не «примерно».
**Стоит на:** снимок `zoe-ci:~/muse-live-src/rootfs-full`, ядро `core-v2/hatch-2026-11-25-v2.bin` и `core-v2-analysis/`; второй образец — `~/ai-retail-brain-v3/zoe/` (как мы уже пересобрали muse).
**Как обманет:** опись по клону `ref/muse` (это не muse, а чужая реконструкция); «у Zoe так» вместо «у muse так»; пропущенная привязка к модели, найденная только в коде П3.

## Что сделать

1. Прочитать опись снимка `rootfs-full.listing.txt`, тексты `opt/hatch-private/prompts/`, конфиги `opt/hatch-private/configs/`, навыки `opt/hatch/`, разбор ядра.
2. Написать `docs/muse_inventory.md` — таблица: вещь muse → где (файл:строка) → что делает → «берём как есть / через прослойку модели / без пары» → чем это у Zoe v3 (если есть, путь).
3. Отдельный раздел «Привязки к модели»: каждое место, где muse опирается на свойства Claude — форма вызова инструментов, мышление, кэш подсказки, сжатие разговора, встроенные инструменты сервера (поиск в сети, выборка страниц — у нас свой инструмент той же формы, работающий с любой моделью), длина окна, картинки и файлы на входе. Для каждого — как это делается у `openai_compat` и у локальной модели, или «у локальной этого нет — возможность выключается».
4. Отдельный раздел «Что можно взять из Zoe v3»: общие модули (область файлов, память, навыки, реестр инструментов, песочница, браузер) — путь, и что в них про сети и должно быть вырезано.
5. Ничего из данных пользователя muse не копировать. Никакого кода в этом срезе.

**Сдача:** ветка `e/P1-inventory`, один файл `docs/muse_inventory.md`, sha — ревизору.
