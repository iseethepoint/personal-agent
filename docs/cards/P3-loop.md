# Карточка П3 — цикл хода (`agent/loop`)

**Кто читает:** ревизор и инженер. На цикле стоят все инструменты (П4), тексты (П5) и вход владельца (П6).
**Решение:** как идёт один ход агента поверх прослойки `agent/model`: модель → пачка вызовов → результаты → модель, со сжатием и подагентами.
**Нормально:** форма и сроки — как у muse (опись, разделы 2.1, 2.8, 2.9, 4.2). Цикл не знает, какая модель под ним: всё, что зависит от модели, берётся из реестра П2.
**Стоит на:** `docs/muse_inventory.md` 4.2; крейт `agent-model` (`Provider`, `Registry`, типы входа и выхода).
**Как обманет:** свои пределы и пороги вместо значений muse; повтор вызова после того, как владелец уже увидел текст; сжатие, теряющее блоки мышления или вызовы без результата; тесты, которые зовут живую модель.

## Общее

- Крейт `agent/loop` (пакет `agent-loop`), async на tokio, как `agent-model`.
- Модель в тестах — поддельный `Provider`, который отдаёт заранее записанную череду `Response`. Нужен общий набор тестов, который гоняется дважды: через поддельный сервер `anthropic` и через поддельный сервер `openai_compat` (правило CLAUDE.md «каждый тест — на двух поставщиках»). Живых вызовов нет.
- Инструменты в П3 — только типаж и тестовые инструменты (эхо, медленный, падающий, с большим выводом). Настоящие инструменты — П4.
- Сроки — по таблице 4.2 описи, значения muse по умолчанию, имена настроек `JARVIS_*` → свои имена, но те же числа; где какое из двух значений тишины (90 / 180 с) — не установлено, берём 90 с (как в П2) и пишем это в коммите.

## П3а — ход и пачка вызовов

Ветка `e/P3a-turn`.

1. Форма — `session/impl_session/message_execution/*` (`source-files.txt:1303-1363`): `model_execution.rs`, `tool_dispatch_batch.rs`, `tool_batch_settlement.rs`.
2. Типаж инструмента: имя, описание, JSON Schema (это `ToolSpec` из П2) и `async fn call(args) -> результат | ошибка`. Реестр инструментов — таблица имя → инструмент; модели уходят описания из реестра.
3. Ход: запрос модели → если в ответе есть вызовы, вся пачка исполняется параллельно → результаты возвращаются одним сообщением в порядке вызовов → снова модель; и так до ответа без вызовов.
   - Неизвестное имя инструмента или неверные аргументы → результат с `is_error`, ход продолжается.
   - Срок на инструмент — 180 с (`JARVIS_TOOL_DISPATCH_TIMEOUT_MS`), по истечении — результат с ошибкой.
   - Блоки мышления и текст рядом с вызовами возвращаются в историю как есть (П2).
4. Большой вывод инструмента — в файл, модели — начало и путь к файлу (`tool_output_spill.rs`, `source-files.txt:1805`). Порог найти в ядре; не найдёшь — так и напиши, ревизор решит.
5. Повтор вызова модели — по правилам muse (`strings-all.txt:54778-54781`): повторяется, только пока владелец ничего не увидел — при ошибке поставщика с признаком «можно повторить», при неверном имени инструмента, при сбое разбора потока. После упора в предел ответа — вставка «Internal retry notice». Число попыток в разборе не найдено: поищи в ядре около `inference_recovery`; не найдёшь — одна повторная попытка, и это названо в коммите.
6. Ответ в заданной форме (`output_contract.rs`, `strings-all.txt:235518`): у весов с `forced_tool_choice` — принудительный вызов; без него — `tool_choice: auto` плюс текст muse «Complete the task by calling `…` exactly once» и проверка, что вызов был ровно один.
7. Тесты: ответ без вызовов; два вызова подряд за один ответ исполняются параллельно (медленный инструмент — время меньше суммы); неизвестный инструмент; срок инструмента; большой вывод; повтор до видимого текста и отказ от повтора после; ответ в заданной форме на обоих видах весов.

## П3б — сборка подсказки

Ветка `e/P3b-prompt`, после «Ок» на П3а.

1. Форма — `prompt_assembly/*` (`source-files.txt:1365-1394`): `prompt_prefix_pin*`, `volatile_context_pin.rs`, `tool_namespace_descriptions.rs`, `context_estimate.rs`.
2. Неизменное начало (системный текст, файлы домашней папки `AGENTS.md`, `SOUL.md`, `IDENTITY.md`, `USER.md`, `MEMORY.md` — `strings-all.txt:59646-59655`, описания инструментов) собирается один раз за разговор и не меняется от хода к ходу. Изменчивое (время, откуда пришло сообщение) — заметкой `Role::Developer` в хвосте.

4. Тексты muse в П3б не переносятся (это П5) — только механизм; в тестах — свои короткие тексты.
5. Тесты: начало подсказки байт в байт одинаково между ходами; время уходит в хвост; оценка длины.

## П3в — сжатие и сброс памяти

1. Форма — `hatch-compaction` (`source-files.txt:2145-2150`), `eager_compaction*` (`:1221-1223`), `compaction_model.rs` (`:1310`), `memory_flush/*` (`:1296-1302`); тексты `P/hatch-compaction/prompts/compact/*.md`, `P/hatch-agent/prompts/session/memory_flush_prompt.md`.

3. После сжатия: сводка + последние сообщения; ни один вызов не остаётся без результата; блоки мышления последнего хода не трогаются.
4. Тексты сжатия muse переносятся как есть (с названными отличиями) — это первый текст muse в репозитории; путь `prompts/compaction/`.
5. Тесты: ниже порога сжатия нет; выше — сначала сброс памяти, потом сводка на модели обслуживания; после сжатия история проходит проверку поставщика (пары вызов-результат); `compaction_memory_flush_use_main`.
