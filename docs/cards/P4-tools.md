# Карточка П4 — инструменты muse (`agent/tools`)

**Кто читает:** ревизор и инженер. На инструментах стоит всё, что агент делает руками: файлы, команды, сеть, память, расписания, навыки.
**Решение:** какие инструменты muse и в какой форме видит модель; как каждый исполняется у нас.
**Нормально:** имя, описание и параметры — как у muse (тексты из ядра, личный вариант, байт в байт); описание одно на всех поставщиков; инструмент подключается записью в реестре инструментов (`agent-loop`, П3а), без правки цикла.
**Стоит на:** `docs/muse_inventory.md` 2.2, 4.3; крейт `agent-loop` (типаж инструмента, `Tools`, spill).
**Как обманет:** свои описания вместо текстов muse; инструмент, который «работает» только в тесте с подделкой; выход за домашнюю папку агента; секреты в выводе команды.

## Общее

- Крейт `agent/tools` (пакет `agent-tools`), async на tokio.
- Описание каждого инструмента (текст для модели, имена и описания параметров) — из ядра muse (`strings-all.txt`, `tool-schemas.txt`), личный вариант; в коммите — адрес или строка. Чего в ядре нет — так и назвать.
- Домашняя папка агента задаётся при запуске; в тестах — временная папка. Разметка папок — как у muse (`strings-all.txt:59657-59690`: `~`, `~/workspace`, `/tmp`).
- Тесты инструментов — без модели (вызов инструмента напрямую) плюс один ход через цикл на обоих поставщиках на срез.

## П4а — файлы

Ветка `e/P4a-files`.

1. Пути — как у muse: относительный от `~`, абсолютный любой («or any absolute path»); своего сторожа папок нет (правка ревизора 27.11). `muse.read`, `muse.write`, `muse.edit` — форма `file_io*` (`source-files.txt:1571-1579`), `edit.rs`, `edit_matching.rs` (`:1552-1553`).
2. `muse.read` с `offset` и пределом — так, чтобы им читался файл большого вывода из П3а («Use read with path=… offset=… to continue»); единица `offset` должна совпасть с той, что пишет spill.
3. Правка заменой: точное совпадение, иначе понятная ошибка (форма `edit_matching`); несколько совпадений — ошибка.
4. Перевод документов в текст (`file_io/document_convert.rs`, `:1573`) — только если в разборе видно, чем muse это делает; иначе — отложить и назвать.
5. Тесты: чтение с offset продолжает файл spill; запись и правка; правка без совпадения и с двумя совпадениями; путь вне разрешённых папок.

## П4б — исполнение команд

Ветка `e/P4b-exec`, после «Ок» на П4а.

1. `muse.exec` и `process.list/poll/log/write/send_keys/kill/clear` — форма `subprocesses/*` (`source-files.txt:1764-1796`: `exec_tool.rs`, `process_tool.rs`, `executor/local*`).
2. Команда в оболочке, рабочая папка — домашняя; долгая команда уходит в фон и видна через `process.*`; срок и пульс — значения muse (180 с на инструмент, пульс 60 с — опись 4.2).
3. Скрытие секретов в выводе — форма `redaction.rs` (`:1780`): значения переменных окружения с ключами (имена из реестра моделей, `api_key_env`) в выводе заменяются.
4. Изоляция (cgroups, клетка исполнения `runtime-cell`) — не здесь, это П8 (свой сервер).
5. Тесты: короткая команда; долгая — в фон, `poll`, `log`, `kill`; ключ из окружения не виден в выводе; срок.

## П4в — навыки, коннекторы и список дел

Ветка `e/P4c-skills`, после «Ок» на П4б. Базы не нужно — всё на файлах.

1. `muse.skill_search` (`source-files.txt:1735`) и `muse.connector_search` (`:1538`; `P/hatch-agent/prompts/blocks/shared/environment/skills.md:1-2`): поиск по `skill.yaml` / `SKILL.md` и `connector.yaml` / `CONNECTOR.md`. Описания инструментов — из ядра.
2. Папки — как у muse (`strings-all.txt:59686-59689`): системные навыки только для чтения (у нас `skills/` репозитория, путь задаётся при запуске), свои — `~/workspace/custom-skills/`, `~/workspace/custom-connectors/`. Свой навык с тем же именем — поправка поверх системного, как у muse.
3. `include_in_prompt` в `skill.yaml`: такие навыки видны в начале подсказки (П3б), остальные — через поиск. Как muse ищет (по словам, по описанию) — найти в ядре; не найдёшь — по словам в `name`, `title`, `description`, и назвать.
4. Сброс устаревшего навыка после правки (`runtime.skill_invalidation_receipts`, `sql.txt:3645`) — только форма без базы: навык перечитывается с диска, если файл изменился.
5. `todo.write` (`strings-all.txt:58134`, `source-files.txt:1797-1798`): список дел внутри хода, описание из ядра.
6. Навыки muse в этом срезе не переносятся (это П5); в тестах — свои маленькие навыки во временной папке.
7. Тесты: поиск находит системный и свой навык; свой поверх системного; `include_in_prompt` попадает в начало подсказки; правка файла навыка видна при следующем поиске; `todo.write`; один ход через цикл на обоих поставщиках.

## П4г — сеть: поиск и чтение страниц

Ветка `e/P4d-web`, после «Ок» на П4в. Поставщик — Firecrawl (слово владельца 27.11; у muse он — бэкенд инструментов браузера, `strings-all.txt:245415`).

1. `browser.search`, `browser.open`, `browser.find`, `browser.lookup_citation_url` — форма `hatch-agent/src/tools/browser_*.rs` (`source-files.txt:1504-1510`), крейт `web-search` (`:7359-7362`); описания и параметры — из ядра (`strings-all.txt:76891`, правила выбора `:58083-58084`, `R/home/hatch/docs/browser.md:18-20`), личный вариант.
2. Поставщик поиска — запись в настройке агента (адрес, имя переменной ключа `FIRECRAWL_API_KEY`), как модель в реестре; Firecrawl — первый и пока единственный. `search` → поиск Firecrawl; `open` → выборка страницы Firecrawl в текст (markdown); `find` — поиск по уже полученному тексту страницы, без сети; `lookup_citation_url` — адрес из прошлой выдачи.
3. Как muse держит полученные страницы и выдачу между вызовами (`page_cache`, `cached_page_scroll`, `url_outlink`) — найти в ядре и повторить форму в памяти процесса.
4. Чёрный список адресов muse (`R/opt/hatch-private/configs/blocklist/*`) — как есть: адрес из списка не открывается, с текстом muse.
5. Большая страница — через spill П3а.
6. Тесты: только поддельный сервер Firecrawl на 127.0.0.1 (ответы — по документации Firecrawl); живых вызовов нет — это деньги. Поиск; открытие страницы; `find` по ней; ссылка из выдачи; адрес из чёрного списка; ошибка поставщика; ключ не виден в выводе; один ход через цикл на обоих поставщиках.

## П4д — память на Postgres

Ветка `e/P4e-memory`, после «Ок» на П4г. База — Postgres с pgvector, как у muse (слово владельца 27.11).

1. Postgres для тестов на Mac — Homebrew (`postgresql@17` и `pgvector`), только на `127.0.0.1`, своя база на прогон тестов, после прогона удаляется. Место на диске держать не меньше 20 ГБ. В README — как поставить.
2. Схема — по SQL muse (`core-v2-analysis/sql.txt`, всё с `memory.`: `entries`, `claims`, `embeddings`, `entry_attributes`, `metadata`; столбец `vector(384)`, `strings-all.txt:213514-213517`). Миграции — свои файлы `agent/memory/migrations/`, форма таблиц и запросов — muse. Чего в SQL muse не видно, назвать.
3. Крейт `agent/memory` (пакет `agent-memory`): запись, утверждения (новое заменяет старое — `supersedes_claim_id`), поиск. Поиск двойной, как у muse (опись 4.4): по словам (`websearch_to_tsquery`, `ts_rank_cd`, `strings-all.txt:200441-200454`) и по векторам (cosine), когда в реестре есть модель задачи `Embeddings` (П2в, `embed()`); без неё — только по словам, векторы дозаполняются позже (`strings-all.txt:55090`).
4. Инструменты `muse.memory_search`, `muse.memory_get`, `muse.memory_explain` и забывание (`forget_tool.rs`, навык `forget`) — описания из ядра, личный вариант (`strings-all.txt:59746`, `tool-schemas.txt:24-27`).
5. Файлы памяти `~/MEMORY.md` и `~/memory/` (`strings-all.txt:59655,59667-59671`): как muse связывает их с базой (`ingest`, `reindex`, `source-files.txt:5463-5476`) — найти и повторить форму; `MEMORY.md` уже идёт в начало подсказки (П3б).
6. Фоновая уборка памяти (самоулучшение) — не здесь, это отдельный срез.
7. Тесты: запись и поиск по словам; утверждение заменяет старое; поиск с векторами (поддельный сервер `/v1/embeddings`) и без; забывание; файл `~/memory/…` попадает в поиск; один ход через цикл на обоих поставщиках. Живых вызовов нет.
8. Заодно — `README.md` в корне: rustup, `git lfs install --local && git lfs pull`, Postgres, `cargo test --workspace`.

## П4е — расписания и наблюдатели

Ветка `e/P4f-cron`, после П3д.

1. Форма — `hatch-cron`, `hatch-cron-core` (`source-files.txt:2220-2297`), `hatch-db-scheduler` (`:4880-…`); таблицы `scheduler.jobs`, `scheduler.job_runs`, `scheduler.cron_mutations`, `scheduler.delivery_outbox` (`sql.txt:310,4431,4591,4594,4623`) — схема и запросы по SQL muse, Postgres из П4д.
2. Инструменты `cron.add/list/view/update/remove/run/runs/status/stop` (`P/hatch-agent/prompts/blocks/shared/environment/scheduled_work.md:1`, `strings-all.txt:59588,59594`) и `hooks.list/add/update/remove/dry_run/enable/disable/run/logs/view` (`hooks.md:1`, `source-files.txt:5988-5989`, `runtime.event_hook_admissions` `sql.txt:908`) — описания из ядра, с правками П10.
3. Запуск задания — фоновый ход со своим текстом `P/hatch-cron/prompts/scheduler/worker_instruction.md` и др. (перенести с правками П10, записать в `prompts/SOURCES.md`); модель — задача `CronWorker` (П2а); срок первого куска ответа — 30 мин (`JARVIS_CRON_MODEL_STREAM_FIRST_CHUNK_TIMEOUT_MS`, опись 4.2). Итог — главному агенту заметкой в ящик (как подагенты), он решает, говорить ли владельцу (`R/home/hatch/docs/scheduling-and-watching.md:7-31`).

5. Долг из П4д: сверка файлов памяти с базой — фоновой работой по расписанию, как у muse; из поиска убрать.
6. Тесты: время подделывается (не ждать минуты); задание по cron-строке и разовое срабатывает, итог в ящике; `cron.*` и `hooks.*` через цикл на обоих поставщиках; наблюдатель срабатывает только когда скрипт сказал «да»; сверка памяти идёт фоном.
